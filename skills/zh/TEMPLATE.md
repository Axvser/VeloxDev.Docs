# Cloud Glyph Skills

## 职责

本技能体系为 AI Agent 提供 Wiki 文档编写工作流，你将严格遵循该工作流程，产出符合规范的文档

## 变量约定

> **Wiki_Root** — 产出文档的根目录（即 `skills/` 所在目录的父目录），Agent仅允许在Wiki_Root下创建、修改、删除文档文件

> **Deploy_Mode** — 部署模式：
> - `nested`：Wiki 仓库作为子目录挂在某个项目下；Agent 应文档化父项目（排除 Wiki 自身）
> - `standalone`：Wiki 仓库独立使用；Agent 无法自动发现项目，必须询问用户

> **Solution_Root** — 被文档化项目的解决方案根目录
> - `nested` 模式：由 Agent 自动发现（Wiki_Root 的父目录）
> - `standalone` 模式：由用户提供

> **Project_List** — 被文档化项目的列表。在 `nested` 模式下，排除 Wiki 仓库自身的源码项目（即 CloudGlyph 项目）

> **Language_List** — Wiki 的语言支持范围。Agent 应在第 1 步通过交互工具或直接询问确定用户所需语种，再比对 `languages.json` 验证可用性；不支持的语种记录差异并在最后告知用户，不中断流程。

## 内容模型

Wiki 采用"目录即页面"的组织方式。Agent 必须遵守以下两条核心规则：

> **规则 1：目录名即导航结构** — 每个 Wiki 页面对应一个目录。目录名使用 `{数字}_` 前缀控制排序，如 `0_Welcome`、`01_project_structure`。Agent 在创建目录时须使用合适的数字前缀以保证页面顺序。

> **规则 2：内容文件约定** — 每个目录下有且只有一个名为 `index.md` 的内容文件作为该页面的正文。目录内可包含更多子目录来表示子页面（子页面也遵守规则 1）。

> **规则 3：目录名必须匹配目标语言** — 目录名必须使用内容语言而非英语。例如 `Language_List = ["zh"]` 时，使用 `0_欢迎` 而非 `0_Welcome`、`1_快速入门` 而非 `1_quickstart`、`2_API参考` 而非 `2_api`、`3_架构分析` 而非 `3_architecture`。例外：被普遍认可的原始形式专有名词和品牌名（如 "VeloxDev"、"MVVM"、"AOP"）。

### 内容组织（基于维度决策）

Wiki 采用"目录即页面"的组织方式。Agent **不得仅根据项目数量**来决定结构。而是应判断被文档化目标的**性质**：

#### 决策规则

> **被文档化的目标是一个自成一体的框架、类库或产品吗？**（例如 WPF、Entity Framework、VeloxDev、React、一个 NuGet 库、一个游戏引擎等）

| 如果... | 那么... |
|---|---|
| **是**——它是一个内聚的产品/框架/库 | 始终使用**维度**组织——最外层结构是**固定的**（见下文）。通过模块发现得到的每个功能块作为子页面放入各维度下。 |
| **否**——解决方案是一组彼此独立的应用/工具/服务 | **询问用户**如何组织。列出可用选项让用户决定。不要猜测。 |

> **理由：** 一个有 40+ 个子项目的框架仍然是"一个东西"（框架本身）。一个包含 2 个完全独立的 Web 应用的解决方案是两个不同的东西。仅靠数量无法区分这些情况。

#### 维度组织（适用于框架、类库、产品）

最外层目录结构是**严格固定的**——不由发现的功能分类决定。始终包含以下四个维度：

| # | 目录 | 用途 |
|---|---|---|
| 0 | `0_欢迎/` | 欢迎页面——项目概况总览 |
| 1 | `1_快速入门/` | 快速入门——每个功能块的入门代码示例 |
| 2 | `2_API参考/` | API 参考——每个功能块的完整 API 文档 |
| 3 | `3_SE分析/` | 软件工程分析——文件结构、设计模式、数据流、复杂度 |

然后 `{最后编号}_版权/`（例如 `4_版权/`）作为最后一个页面。

**规则：**

- 每个维度目录直接位于 `content/{lang}/` 下——无 `{产品名}/` 或 `{分类}/` 包裹层
每个**功能块**（通过 Demo→Test→源码发现）获得独立子目录（如 `0_功能块A/`、`1_功能块B/`、`2_功能块C/`），每个包含 `index.md`
- 在 `3_SE分析/` 下：内层结构按 SE Analysis 规范——`0_文件结构/`、`1_功能结构/`、`2_设计模式分析/{Feature}/`、`3_数据流分析/{Feature}/`、`4_复杂度分析/{Feature}/`
- 版权始终是该语言内容树的最后一个编号

## 代码真实性优先层级（关键）

Wiki 文档中的每个代码片段**必须**来自真实源码。Agent 在发现 API 使用示例时须遵循以下严格优先层级：

> **优先级 1（最高）— Demo/示例项目**
> 扫描 `Examples/` 或 `samples/` 目录中的真实使用代码。这些展示了预期的顶层 API 表面和最惯用的模式。
>
> **优先级 2 — 单元测试**
> 从测试文件中提取使用模式（如 `*Test*.cs`、`*Spec*.cs`）。测试使用真实参数和边界情况检验真实 API。
>
> **优先级 3（兜底）— 源码自行发现**
> 仅当某模块既无 Demo 也无测试时：读取源码接口，提取方法签名，构造最小使用示例。若未经实际调用点验证，必须明确标注为*推断所得*。
>
> **规则 1（强制完整阅读）：** 如果某模块存在 Demo 代码（优先级 1），Agent **必须完整阅读该模块 Demo 目录下的所有源文件**，不得仅挑选几行片段就略过。读完后须在文档中体现 Demo 所展示的全部使用模式——包括初始化、配置、核心 API 调用链、错误处理和边界情况。同理，若没有 Demo 但有测试，则必须完整阅读测试文件。
>
> **规则 2（无编造）：** 如果代码块中包含代码库中不存在的类名、方法名或 API 调用，即为**编造**，必须在审核步骤前修复。Agent 须通过搜索实际源文件来验证每个引用的符号。

## 代码样式

SKILL 系统对文档代码块中的代码缩进或格式化风格**无任何要求**。Agent 应沿用项目源文件中已有的缩进风格（Tab 或空格等），或使用能产生可读性良好、一致输出的任意风格。

## 工作流

> 0.开始

> 1.部署模式检测与变量确认

> 2.技术栈分析

> 3.约束加载

> 4.功能模块发现

### 内容编写阶段（步骤 5-8）

页面按**读者消费顺序**编写：快速入门 → API → 架构分析 → 版权。此顺序确保前面的页面可以在适当位置引用后面的页面。

#### ⚡ 按模块微循环（Steps 5→6→7）

当 `Project_List` 包含**多个模块**时，步骤 5→6→7 按**每个模块执行微循环**，而非先对所有模块批量写快速入门、再批量写 API。这防止 Token 爆炸和上下文丢失，并确保每个模块的 API 和分析章节能受益于刚写完的该模块专属快速入门。

**前置步骤（每个模块必须执行）：** 在进入微循环前，Agent **必须完整读取**该模块的全部 Demo/Test 源文件，形成对该模块 API 表面的完整认知后再编写。不得仅阅读部分文件就开始编写。

**正确模式——按模块微循环：**
```
对于 模块A：
  前置：完整阅读模块A 的所有 Demo/Test 源文件
  5.编写【模块A 的快速入门】
  6.编写【模块A 的API参考】
  7.编写【模块A 的架构分析】
对于 模块B：
  前置：完整阅读模块B 的所有 Demo/Test 源文件
  5.编写【模块B 的快速入门】
  6.编写【模块B 的API参考】
  7.编写【模块B 的架构分析】
...（对每个模块重复）
然后 8.编写【版权】（全局，一次完成）
```

**错误模式——按步骤批量（不要这样做）：**
```
5.编写【所有模块的快速入门】    ← Token 爆炸，上下文丢失
6.编写【所有模块的API参考】
7.编写【所有模块的架构分析】
```

对于**单项目**层级（仅 1 个模块），微循环自然坍缩为一次迭代，按相同方式处理即可。

> 5.编写【快速入门】— `1_快速入门/{Feature_N}/`（例如 `1_快速入门/0_功能块A/index.md`，含入门代码示例）

> 6.编写【API 参考】— `2_API参考/{Feature_N}/`（例如 `2_API参考/0_功能块A/index.md`，完整 API 参考文档）

> 7.编写【软件工程分析】— `3_SE分析/.../{Feature}/`（架构、类图、时序图）。在 `3_SE分析/` 下，每个子组（`0_文件结构/`、`1_功能结构/`、`2_设计模式分析/`、`3_数据流分析/`、`4_复杂度分析/`）包含各功能块的子页面。

> 8.编写【版权】— `{N}_版权/`（例如 `4_版权/index.md`），其中 `N` 为该语言下最后一个编号

### 润色与发布阶段（步骤 9-11）

> 9.编写【欢迎页】— `0_欢迎/`（英文为 `0_Welcome/`）。在所有内容页面编写完成后、审核之前执行。欢迎页总结所有其他页面。

> 10.【审核 — 质量门 🔴 必需】— 加载 `skills/zh/review/SKILL.md` 并逐项执行检查清单，至少包含以下审计：
>     - 模块覆盖率：对照模块列表验证每模块均已文档化
>     - 代码真实性：对每页的每个代码块，验证类名/方法名/参数/命名空间与源码一致
>     - 图表语法：Mermaid/PlantUML/KaTeX 语法验证
>     - 结构一致性：数字前缀、index.md 存在性、无本地 Markdown 链接
>     - 导航索引：运行 `python gen_tree.py` 重建 tree.json
>     - 项目构建：运行 `dotnet build` 验证编译通过

> 11.结束

### 工作流连续性

工作流**绝不能因工具调用次数限制、Token 限制、超时或其他基础设施约束而自动静默终止**。如果 Agent 达到执行限制或遇到中断：

1. **不得编造结果**用于模拟完成
2. **记录观察**记录工作流停止的位置和已完成的工作
3. **询问用户**是否继续，提供当前进度摘要和预估剩余工作量
4. 在用户确认后从记录的检查点恢复执行

此规则适用于所有阶段：模块发现、内容编写和审核。仅当用户明确同意提前终止时，部分输出才可接受。
