## 分析范式

⚙ **Wiki 的内容以「功能」为基本单元进行划分，而不是以 Project 的目录结构进行划分**。目录结构是项目的一种实现细节，可能随架构演进、团队习惯而变化，不应直接映射为 Wiki 结构。

⚙ 功能（Feature）的定义：一个功能是项目对外提供的一组内聚能力，通常对应一个可独立描述、独立使用、独立验证的使用场景。同一功能可能横跨多个目录/工程，同一目录下也可能并存多个功能——判定以功能为准，目录仅作为查找线索。

⚙ 功能/API 的发现顺序与路径（按优先级从高到低）：

1. **入口理解** — 先阅读项目的 README、入口文件、构建脚本等，建立对项目整体意图的认知，形成候选功能列表
2. **Demo / Example 优先** — 扫描 Examples/、samples/、demo 等目录并完整阅读全部源文件，Demo 是功能与 API 的第一证据源
3. **测试驱动** — 某个功能若缺少 Demo，完整阅读对应测试文件，从用例中提取功能边界与典型用法
4. **源码兜底** — 仅当以上均缺失时才从源码目录结构与接口签名推断功能，此类推断必须明确标注为「推断所得」

⚙ 上述顺序适用于所有项目规模：单工程、多工程、大型框架/单体仓库一视同仁；大型项目尤其禁止仅凭目录名猜测功能。

⚙ 分析产物：一份「功能清单」，逐项列出 功能名 / 归属工程 / 对外 API 面 / 证据来源（Demo / Test / 推断）。该清单是后续【快速开始】【API】【SE分析】各阶段统一的工作输入，三个阶段围绕同一份功能清单展开，保证 Wiki 各维度口径一致。

⚙ 「功能清单」同时携带每个功能的**覆盖率状态**字段（`TODO / QS ✓ / API ✓ / SE ✓`）。第 3–5 步在完成某个功能时更新该字段；第 8 步【审核】将其对账为「覆盖率对账矩阵」。功能集合在发现完成后**冻结**——后续步骤只允许标记状态，不得增删或改名功能；任何修正必须回填清单并复核。

⚙ Wiki 的五个固定维度（见【结构约定】）下的子项展开一律以功能为单位组织。

## 结构约定

⚙ {ID}_{PageName}/ - 产出Markdown时采取的文件夹命名规则，文件夹构成的树结构就是最终App渲染Wiki时看到的目录结构

⚙ index.md - 每个{ID}_{PageName}/下都必须有且仅有一个固定名称的index.md文件，否则将导致目录结构不完整，md文件可留白，可以加更多子目录表示子项

⚙ 输出路径下的**每一个**目录都必须包含 index.md——包括中间父目录，不仅限于叶子目录。创建新的子目录后，立即确认该路径的每一级祖先目录都有 index.md。常见错误是创建了例如 `2_设计模式/0_工作流/index.md` 但遗忘了 `2_设计模式/index.md`。

最终，目录会呈现下述结构，这是五个固定的维度

> Wiki_Root/0_欢迎/

> Wiki_Root/1_快速开始/.../

> Wiki_Root/2_API/.../

> Wiki_Root/3_SE分析/.../

> Wiki_Root/4_版权/.../

## 目录命名

⚙ 按层级命名：
- **顶层——五个固定维度（一位数字前缀）：** `0_欢迎` / `1_快速开始` / `2_API` / `3_SE分析` / `4_版权`。
- **任意深度的每个子层（两位数字前缀 `NN_`，`00`–`99`）：** 中文 Wiki 用中文命名，英文 Wiki 用小写 kebab-case，**不得含空格**。例如 `00_用户注册/`、`01_数据导出/`。

⚙ **粒度规则：** 一个目录 = 一个「可独立描述、可独立使用、可独立验证的能力单元」。每个维度下每个功能恰好一个目录；不得把多个功能合并进同一目录，也不得把一个功能拆成多个同级目录（应使用嵌套）。功能名一律取自「功能清单」，写时不得现造。

⚙ **跨维度命名一致性：** 同一功能名必须在 `1_快速开始`、`2_API`、`3_SE分析` 三个树中完全一致（按语言）。在快速入门中写成 `00_用户注册`，API 与 SE 分析中也必须写成 `00_用户注册`。

⚙ 复杂功能可继续嵌套子能力（如 `00_用户注册/00_邮箱验证/`），每一级都遵守相同的两位数字 + 中文命名规则。

⚙ **数字前缀只是路径装置，绝不是标题。** `0_Welcome`、`1_快速开始`、`00_用户注册` 是目录名。一旦文本要**呈现给读者**——标题、链接文字、导航路径、表格中提及某页面的单元格——前缀就必须去掉：写 `快速开始`、`用户注册`。渲染器自身（`gen_tree.py`）在生成导航标题时就会剥离前缀，因此正文里手写的 `1_快速开始` 永远是缺陷，而不是与侧边栏对齐。只有两处保留前缀：链接**目标**（`../1_快速开始/index.md`），以及明确在讨论目录结构本身的文字。

⚙ **功能名是功能名，不是类名。** 功能目录为读者寻找的**能力**命名（`用户注册`、`数据导出`），取自「功能清单」。类型名、类名、命名空间名属于页面正文，绝不属于目录名。

⚙ **标题绝不重复其上方标题。** 页面以一个 H1（即页面标题）开头，紧随其后的标题必须说出 H1 尚未说过的东西。以下两种形态都是缺陷：

- **复述链。** `# 工作流系统 — 快速开始` 后接 `## 工作流系统`、再后接 `### 快速开始`，读者在读到任何正文之前先看到同样几个词三遍。页面标题就是标题；删掉重复它的这些标题，并把它承载的内容上提。
- **维度回声。** 紧跟 H1 之后、整行文字恰好是父维度名的标题（`1_快速开始` 下的 `## 快速开始`，`2_API` 下的 `## API`），只告诉了读者侧边栏早已显示的信息。应直接从第一个真正的章节开始。

两种情况都不得丢内容：删掉这类标题意味着把它下辖的子标题整体上提一级，而不是删掉那一节。`validate-titles.py` 对两种形态都会报错；某个名字是否已经说过，以侧边栏为准。

⚙ **页面聚焦上限与叶子预算（默认拆分）：** 功能页不是单一的巨型文档——拆分为默认动作，而非例外。**没有子页的页面称为「叶子页」**，应控制在**约 300 行以内**且最多涵盖**3 个不同主题**。当叶子页将要超出该预算时，沿能力/操作/端点/类型边界把它拆成 **2 个以上的子页目录**（如 `00_{功能}/00_{操作}/index.md`），子页再长大则递归继续拆。此时每个父级 `index.md` 只作为**简短概览**（远低于约 200 行），并用【链接与导航】的跨页链接语法**链接它的每一个直系子页**。

⚙ **大纲先行（强制顺序）：** 需要拆分时，不要先把长文写完再回头拆。应**先**创建计划好的子页目录——每个子目录都放一个（可先为空的）`index.md`，并确保该路径每一级祖先目录的 `index.md` 都在位——随后运行 `gen_tree.py` 让骨架出现在导航里，**之后才**逐叶在预算内填写内容。要「朝已存在的大纲去写」，而不是写成一个默默变长的单页。

⚙ **深度按维度各自免费：** 功能下的子页在各维度彼此独立——QuickStart 树按 安装/操作 拆分，API 树按 命名空间/类型 拆分，SE 树按 页面分组 拆分——一个维度里嵌得更深，绝不迫使另一维度做同样拆分。只有功能自身的顶层名字必须在 `1_QuickStart` / `2_API` / `3_SE_Analysis` 中保持一致。

⚙ **原子页是显式选择而非默认：** 确需保持单页的文档（逐字许可协议/AUTHORS 文本、单一自包含规格）可把 `<!-- cg:atomic -->` 放在其 `index.md` 的**首行**以豁免行数预算；`4_Copyright` 维下的页面自动豁免。请克制使用——这是逃生通道，且门禁真实存在：`python validate-structure.py` 会报告每个超过硬上限的叶子页，以及每个未链接其某个子页的父级概览。

## 本地化

⚙ **每一个页面标题都用本 Wiki 自身的语言书写。** 产出某个语言树时，每个目录名与每个页面标题都必须翻译——`00_workflow-system` 要写成 `00_工作流系统`，而不是照抄英文目录。这并非可选的润色：侧边栏渲染的正是目录名，未翻译的目录名会在整篇已翻译的 Wiki 里直接显示为突兀的英文。

⚙ **唯一的例外是代码标识符。** 若某个目录名**本身就是**源码中的公开类型、特性、命名空间或 API 名称——`MVVM`、`AOP`、`MonoBehaviour`、`00_VeloxPropertyAttribute`、`00_transitionsystem`——则它在所有语言中都原样保留，因为翻译它会让读者无法按名检索。判定标准是机械的、而非审美的：**该字面量是否作为类型/命名空间/API 名出现在源码中？** 是，则保留；若它只是一个描述性英文短语（`prerequisites`、`install`、`complete-code`、`attached-behaviors`、`patterns-overview`），那就是翻译遗漏，必须翻译。

⚙ 两种语言必须在**结构**上对齐（数字前缀拓扑一致，由 `validate-structure.py` 机器校验），并在**语义**上对齐——一种语言中某页的标题，就是另一种语言中同一位置标题的译文。

## 链接与导航

⚙ Wiki 页面中只允许出现以下三种链接：

1. **外部链接** — 目标以 `https://`、`http://`、`mailto:` 或 `tel:` 开头，由系统浏览器 / 邮件客户端 / 拨号程序打开。谨慎使用。
2. **同语言跨页链接** — 相对 Markdown 链接，目标按文件系统规则解析（遵循 `.`/`..`），最终落在**同一语言树内的另一个页面目录**上。目标以目录路径结尾即可，也可显式写 `/index.md` 或以 `/` 结尾。必须使用**含数字前缀的真实目录名**（`0_Welcome`、`00_用户注册`），严禁使用显示标题。禁止跨语言链接。
   示例（页面 `1_快速开始/00_用户注册/index.md` 内）：
   - 同功能内的子页：`[邮箱验证](00_邮箱验证/index.md)`
   - 同一栏目下的兄弟页：`[数据导出](../01_数据导出/index.md)`
   - 栏目概览（父级）：`[快速开始概览](../index.md)`
   - 任意顶层栏目：`[欢迎页](../../0_欢迎/)`
   父级 `index.md` 链接其子页，用的正是该语法。
3. **页内锚点** — `#slug`，指向**同一页面**内的某个标题。App 依据标题的最终文本自动生成 id（slug）：转小写；保留字母、数字、`_`、`-`（CJK 汉字原样保留）；删除其余字符（`.`、`:`、`(`、`)` 等）；空格与 `_` 转为 `-`；合并连续 `-` 并去掉首尾 `-`；重名时依次追加 `-1`、`-2`…。仅对文本干净、无标点的标题手写 `#…` 锚点——例如标题 `## 2. 文本格式` → `#2-文本格式`；标题 `## 概述` → `#概述`。

⚙ **链接文字绝不含数字前缀。** 目标是路径，保留前缀（`../1_快速开始/00_用户注册/index.md`）；可见文字是散文，不得保留（`[快速开始](../1_快速开始/index.md)`、`[用户注册](../1_快速开始/00_用户注册/index.md)`）。`[1_快速开始](../1_快速开始/index.md)` 是缺陷。链接文字应是该页的纯标题——即侧边栏显示的那个字符串——或是在句中读得通的自然短语。

⚙ **禁止：** 其它任何本地/绝对/`file:` 链接、指向其它语言内容的链接、越出语言根目录的链接、携带 `#` 的跨页目标，以及无法解析到真实页面或标题的目标。不确定时不要写链接。

## 渲染成员

⚙ 除普通 Markdown 外，正文还可使用下述围栏代码块。每一种都有对应校验器；格式错误时它会渲染成一个静默的空白，因此要校验而非假设。

| 围栏 | 用途 | 校验器 |
|---|---|---|
| `mermaid` | 流程图、时序图、类图、状态图、ER 图、git 图 | `validate-mermaid.js`（真实解析器）/ `validate-mermaid.py` |
| `plantuml` | API 调用时序、组件与部署图 | `validate-plantuml.py --engine java` / `validate-plantuml.py` |
| `plot` | **数学曲线**——见下 | `validate-plot.py` |
| `video` | B站 / YouTube / Vimeo 视频嵌入 | — |

⚙ **函数图像（`plot`）——当主题本身就是一条函数时，请画出来。** 描述一条曲线、一段响应、一次衰减或一族缓动函数的页面，应当把它画出来，而不是用文字描述或表格罗列。正文是一个 **JSON 对象**（[function-plot](https://mauriciopoppe.github.io/function-plot/) 的配置项），因此数字必须是 JSON 数字——`2*PI` 非法，`6.283185307179586` 才行：

````markdown
```plot
{
  "title": "easeInOutQuad",
  "grid": true,
  "xAxis": { "domain": [0, 1] },
  "yAxis": { "domain": [0, 1] },
  "data": [
    { "fn": "x < 0.5 ? 2*x^2 : 1 - (-2*x + 2)^2/2" }
  ]
}
```
````

⚙ 容易踩的规则：常量是**大写**的（`PI`、`E`——小写 `pi` 未定义，曲线会静默消失）；`"data"` 是由对象组成的数组，对象含 `fn`（或 `x`/`y`/`r`）；分段曲线用三元运算符 `?:`；非 `y = f(x)` 的图类型（`fnType` 为 `parametric`/`polar`/`points`/`vector`，或 `graphType` 为 `scatter`）还须加 `"sampler": "builtIn"`，且参数名在参数方程中是 `t`，在极坐标中是 **`theta`**；幂的指数只能是字面整数——指数含变量（`2^x`、`2^(10*x - 10)`）或为小数（`x^0.5`）时区间采样器回空区间，曲线静默不画，要改写成 `exp(u*ln底)`。定义域要收紧到真正有信息量的区间——默认缩放往往什么都看不出来。

## 编码风格约定

⚙ **代码缩进一律使用实际空格字符（Space），禁止使用制表符（Tab / \t）**。所谓缩进，是指确定数量的空格，例如 4 个空格；Tab 在不同渲染环境下的显示宽度不可控，不允许出现在 Wiki 代码块中。

⚙ 在编写 Wiki 代码块前，扫描【Project_Root】下的源文件检测项目的主导缩进宽度（2 空格、4 空格等），生成的代码块缩进必须与其匹配。检测有歧义时默认使用 **4 空格**。

⚙ 从源文件（Demo / Test / 源码）提取代码片段时，将源文件中的制表符统一转换为检测到的空格宽度（默认 4 空格），确保 Wiki 内所有代码块均为实际空格缩进。
