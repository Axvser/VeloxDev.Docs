# 弱引用类型 — 选择集合类型

四个类型解决不同类别的泄漏/生命周期问题。先用下面的表选定，再跳到对应页面。

## 1. 场景对照表

| 场景 | 类型 | 原因 |
|---|---|---|
| 一个事件式发布者，不能把已死订阅者保活（“弱事件”） | `WeakDelegate<TDelegate>` | 每个处理器是 `WeakReference<Delegate>`；订阅者被回收后，该处理器在下一次重建时消失。见[弱委托订阅](../03_弱委托订阅/)。 |
| FIFO 缓冲中的条目不能把它们的产生者钉住 —— 只在产生对象仍存活时处理这些工作 | `WeakQueue<T>` | 条目是 `WeakReference<T>`；只被队列引用的条目可被回收，访问会跳过/剪除死条目。见[弱队列](../04_弱队列/)。 |
| LIFO（撤销/重做、回退栈）中短命状态不能让自己的所有者一直可达 | `WeakStack<T>` | 与队列相同的弱条目模型，LIFO 顺序。见[弱栈](../05_弱栈/)。 |
| 一个“按目标键”的值，目标键一消失值也随之消失（临时旁表） | `WeakCache<TTargetKey, TCacheKey>` | 建立在 `ConditionalWeakTable<TTargetKey, TCacheKey>` 上，它不会把键保活。见[弱缓存](../06_弱缓存/)。 |

**预期结果：** 对每一行，你在读详细页面之前就能说出确切的泛型类型——包括它的类型实参。

## 2. 共同的约束

泛型约束直接来自 `Src/Core/VeloxDev.Core/WeakTypes/` 里的源码签名：

- `WeakDelegate<TDelegate>` 要求 `where TDelegate : Delegate` —— 处理器必须是委托实例。
- `WeakQueue<T>` 与 `WeakStack<T>` 要求 `where T : class` —— 条目必须是引用类型。
- `WeakCache<TTargetKey, TCacheKey>` 要求 `where TTargetKey : class` **且** `where TCacheKey : class` —— 键与值都是引用类型。

值类型（如 `int`、`struct`）在编译期被拒绝，因为 `WeakReference<T>` 只能追踪引用类型目标。若确需为值开一个弱槽，把它包进一个小类，或用你自己的生命周期规则去守卫一个可空字段。

**预期结果：** 编译器接受 `WeakQueue<SomeClass>`，拒绝 `WeakQueue<int>` 并报约束错误。

## 3. 何时不要用弱集合

- **你需要在集合存活期间条目也一直存在。** 弱集合不是保证 —— 只有一个弱引用在撑着的条目可能随时被 GC 回收。若正确性要求条目必须存在（一个你稍后要排空的真实工作队列），请在其它的地方保存强引用。
- **你已经掌控生命周期。** 如果订阅者/所有者与事件源的寿命明确且有界、由你管理，显式退订（或从集合移除）比依赖 GC 更廉价、更可预测。
- **你需要跨 GC 的 `IEnumerable` 顺序保证。** 枚举会剪除并只产出存活条目，因此两次枚举之间若发生一次 GC，可见内容可能变化。
- **键/值是驻留字符串或静态字符串。** 字符串字面量在整个进程生命周期内都被运行时钉住，所以建立在字面量上的 `WeakCache<string, string>`（正如某些单元测试）实际上从不驱逐。想观察驱逐要用真实对象实例。见[GC行为与注意](../07_GC行为与注意/)。

**预期结果：** 对每个“不要”情形，你都能说出自己*不会*选哪个类型以及为什么。
